### Ring buffer algorithm (exact mechanics)

Two separate `deque`s exist in the main loop:
1. `ring_buf` — a `collections.deque(maxlen=buffer_chunks)` of raw PCM byte chunks, continuously `.append(data)`-ed every capture iteration (`detector.py:513-514`). This is the **pre-trigger** buffer — a fixed-size circular buffer; once full, appending evicts the oldest chunk automatically (deque's native behavior).
2. `analysis_buf` — separate `deque(maxlen=analysis_chunks)` used only for cross-correlation scoring (not needed for your port).

When a trigger fires (either the MQTT trigger_event or a cross-correlation detection), the flow is (`detector.py:517-543` for MQTT trigger path, `552-573` for detection path — logic is identical):
```python
pre_frames = list(ring_buf)                       # snapshot everything currently buffered
post_chunks = max(1, int(args.post_trigger_seconds / chunk_size_s))
post_frames = []
for _ in range(post_chunks):
    try:
        post_frames.append(stream.read(chunk, exception_on_overflow=False))
    except OSError:
        log.warning("Buffer overflow during post-trigger collection")
        break
threading.Thread(target=save_clip, args=(pre_frames + post_frames, filepath), daemon=True).start()
```
Key facts:
- **Pre-trigger frames**: whatever is currently in the ring buffer (up to `buffer_chunks` chunks) at the instant of trigger — this is "look-back" audio already captured before the event.
- **Post-trigger frames**: captured synchronously in a blocking loop *after* the trigger, by calling `stream.read()` directly (not going through the deque) — this **blocks the main capture loop** while collecting post-trigger audio (a known repo caveat: "Cross-correlation is slow enough to drop audio in saved clips if not handled carefully", CLAUDE.md:238).
- The concatenation `pre_frames + post_frames` is written to disk via `save_clip()`, called in a **daemon background thread** so file I/O doesn't block capture.
- Chunk size = `chunk_size_s = args.chunk_size_ms / 1000.0` (default 500 ms → 0.5 s), `chunk = int(RATE * chunk_size_s)` samples per read (`detector.py:425-426`).

### Clip duration

## 5. `data_collector.py` vs. `detector.py` — which is the better MQTT-trigger-plus-ring-buffer reference

**`data_collector.py` is the better reference for this specific feature.** Its save/trigger path is simpler, cleaner, and *not* commingled with cross-correlation timing constraints:

- Single unified `audio_buffer` deque used both as the live ring buffer AND the pre-trigger snapshot source (no separate scoring-buffer complexity) — `data_collector.py:301-303, 374`.
- `save_audio()` (`data_collector.py:64-80`) is a clean, synchronous helper combining ring-buffer snapshot + blocking post-trigger reads + WAV write, called directly (not backgrounded in a thread) with an `is_saving` guard flag to prevent overlapping saves (`data_collector.py:379, 385, 404, 411`) — this is arguably a **simpler and more robust mental model** for the ESP32 port than `detector.py`'s fire-and-forget daemon-thread approach, since embedded environments benefit from explicit state flags over Python threading.
- Filename pattern: `f"recording_{ts}.wav"` with `ts = datetime.datetime.now().strftime("%Y-%m-%d_%H-%M-%S")` (`data_collector.py:380-381, 405-406`) — simpler/more generic than detector.py's `doorbell_`-prefixed names, good default if you don't want detection-specific naming.
- MQTT setup (`setup_mqtt()`, `data_collector.py:87-137`) is functionally **identical** to `detector.py`'s (same connect/tls/on_message/trigger_event.set() pattern) — topic is `--mqtt-topic` default `"doorbell/trigger"` (`data_collector.py:230-233`), with the same `--mqtt-trigger-value` exact-match-or-any-message semantics (`data_collector.py:121-125`).
- It additionally demonstrates a GPIO physical-button trigger sharing the same `trigger_event` (`data_collector.py:140-154`) — a useful pattern if the ESP32-S3 project ever wants a manual button alongside MQTT.
- It reopens the audio stream on `OSError` (buffer overflow) rather than just logging and continuing (`data_collector.py:413-421`) — more resilient error handling to mirror in firmware.

`detector.py`'s ring-buffer/save code is functionally similar but structurally entangled with the cross-correlation `analysis_buf` and threaded background writes, plus two divergent trigger-vs-detection code paths that duplicate the save logic (lines 517-543 and 552-573 are near-identical copy-pasted blocks) — a maintenance smell you don't need to replicate.

**Recommendation**: model the ESP32 port's ring-buffer + MQTT-trigger + WAV-save logic on `data_collector.py`'s `save_audio()` + `setup_mqtt()` + `is_saving` guard pattern, using `detector.py` only for the exact WAV constants (`CHANNELS=1`, `paInt16`→16-bit signed, `RATE=16000`) and its two-tier `on_connect`/`on_message` MQTT plumbing (both scripts implement this pattern identically, so either works as the MQTT reference).

## 3. Concurrency Model

**Simplification over a naive 2-explicit-tasks design:** the Arduino core already runs `loop()` as its own FreeRTOS task (`loopTask`, pinned to core 1 by default on ESP32). Leverage that instead of spawning a redundant audio task — put the PDM read / ring-buffer / trigger-handling sequence directly in `loop()`. Spawn exactly **one** additional task, `networkTask`, pinned to core 0, running WiFi/MQTT service + the upload scheduler poll. This is fewer moving parts for the same effective two-core split.

- **Trigger handoff** (net task → audio/loop task): `mqtt_client`'s `on_message` callback (runs inside `mqttClient.loop()` on core 0) calls `xTaskNotifyGive(loopTaskHandle)`. `loop()` polls non-blockingly each iteration with `ulTaskNotifyTake(pdTRUE, 0)`. This is the FreeRTOS-native, zero-extra-object way to move a single boolean event across cores — no custom queue/semaphore struct needed.
- **`is_saving` guard** (ported from Pi): a `volatile bool isRecording` checked in `loop()` before consuming a notification. A second trigger arriving mid-recording is simply left un-consumed (task notifications coalesce a pending "1" rather than queuing multiple) — this reproduces the Pi's "ignore concurrent triggers" behavior with less code than a semaphore, matching your "pick the simpler one" call.
- **Ring buffer**: owned exclusively by the loop-task/core-1 — no lock needed since nothing else ever touches it.
- **SD card — the one real gap in your draft spec to flag:** SD/SPI is touched by *both* tasks (audio task writes the WAV; network task lists/deletes during upload). The Arduino `SD`/`SPI` stack is not safe for concurrent access from two cores. **This needs a mutex** (`SemaphoreHandle_t sdMutex`, created in `sd_storage::begin()`), taken by both the WAV-write step and every upload-scan/delete step. This wasn't explicit in your draft ("communicating via a queue/flag/semaphore for trigger/file-ready") — the trigger handoff needs a notification, but the SD card needs a true mutex because it's genuinely shared mutable state accessed from two cores, not just a producer/consumer signal.

## 4. Key Algorithms

**Ring buffer:** `heap_caps_malloc(BUFFER_SECONDS * 16000 * 2, MALLOC_CAP_SPIRAM)` (96 KB for 3s). Circular byte array with `writePos`; each PDM read chunk copied in with wraparound (two `memcpy`s if the chunk straddles the end). Always "live" from boot — first 3s of pre-roll before the buffer fully wraps will just be silence/zeros, which is an acceptable, unavoidable cold-start edge case.

**Trigger → save sequence** (mirrors Pi's blocking-append model, in `loop()`):
1. Notification observed, `!isRecording` → `isRecording = true`.
2. Allocate/reuse a PSRAM clip buffer sized `(BUFFER_SECONDS + POST_TRIGGER_SECONDS + margin) * 32000` bytes (~320 KB for 3s+6s+1s margin).
3. Copy ring buffer into the clip buffer in chronological order (oldest-to-newest, 1–2 `memcpy`s depending on wrap position).
4. Continue reading PDM chunks, appending directly to the clip buffer (not to the ring buffer — matches Pi's behavior of the ring buffer being paused during a save), until total length reaches the target.
5. Generate filename via NTP-synced localtime: `doorbell_manual_%Y%m%d_%H%M%S.wav`. **Edge case to flag:** if NTP hasn't synced yet (e.g., trigger fires seconds after boot before WiFi/NTP settle), fall back to a `millis()`-based sequential name so the file isn't silently dropped.
6. Write to a temp name (`/recordings/.tmp/&lt;name&gt;.wav` or `&lt;name&gt;.wav.tmp`) under the SD mutex, then rename to the final `.wav` name only after a successful close. **This atomic-rename step is a recommended addition**, not in your draft: without it, a crash/reset mid-write leaves a truncated file with a garbage RIFF size that the upload scanner (which just globs `*.wav`) would happily try to upload.
7. `isRecording = false`.

**WAV header** (`wav_writer`): standard 44-byte canonical header — `RIFF/WAVE/fmt /data`, PCM format 1, 1 channel, 16000 Hz, 16-bit, block align 2, byte rate 32000. No library needed; hand-write the struct.

**SigV4 signer** (single PUT, no multipart, no query string):
- Canonical request → string-to-sign → `HMAC` chain (`AWS4"+secret → date → region → "s3" → "aws4_request"`) → hex signature → `Authorization` header, all via `mbedtls_sha256`/`mbedtls_md_hmac` (bundled with the ESP32 Arduino core — no extra lib_dep).
- **Recommended simplification over your draft:** use `x-amz-content-sha256: UNSIGNED-PAYLOAD` instead of hashing the actual file body. Hashing the real payload would require reading the ~288 KB clip from SD twice (once to hash, once to stream) for negligible security benefit on a private LAN. MinIO accepts `UNSIGNED-PAYLOAD`. This halves SD I/O per upload and removes a class of bugs.
- Body streaming: `HTTPClient::sendRequest("PUT", &amp;sdFile, fileSize)` accepts a `Stream*` directly — `File` extends `Stream`, so this satisfies the "streamed from SD, not loaded fully into RAM" requirement with zero custom chunking code.
- Region: MinIO doesn't enforce it meaningfully; hardcode `us-east-1` as a build flag default.

**Daily upload scheduler:** poll every ~10 min from `networkTask`:
```
if (!ntp_time::isSynced()) return;
tm = ntp_time::localNow();
if (tm.tm_hour == 3 &amp;&amp; !uploadedToday) { runUpload(); uploadedToday = true; }
if (tm.tm_hour != 3) uploadedToday = false;   // re-arm once we leave the 3 o'clock hour
```
**Recommended addition** (not in your draft): also run `runUpload()` once immediately after every successful boot + WiFi + NTP sync, in addition to the 3am trigger. Rationale: with the pure-RAM `uploadedToday` flag, a reboot at 3:05am (power blip) means that day's recordings wait a full 24h before the next attempt. A cheap boot-time catch-up closes that gap at near-zero cost, since the upload routine already tolerates being called redundantly (nothing left to upload = no-op).

## 7. Confirmed / Called-Out Design Decisions

- **I2S API:** use the newer explicit-mode API (`I2S.setPinsPdmRx(42,41)` + `I2S_MODE_PDM_RX`/`I2S_SLOT_MODE_MONO`) rather than the legacy `setAllPins`/`PDM_MONO_MODE` call — it's the actively maintained path in current arduino-esp32 cores. This is *why* the platform version needs to be pinned explicitly rather than left floating.
- **No TLS for MQTT or MinIO:** confirmed correct given the repo's own `.env` already points at MinIO over plain HTTP, and the existing project's MQTT design doc also assumes plain broker access on the LAN. Removes `WiFiClientSecure`/cert-bundling complexity entirely for v1.
- **Once-daily directory scan is sufficient:** confirmed, with the boot-time catch-up added as a low-cost safety net (§4).
- **Single-PUT, no multipart:** confirmed, clips are ~288 KB.

## 8. Flagged Issues / Missing Edge Cases (beyond what's already threaded above)

1. **SD mutex is a hard requirement, not optional** — the one place this design needs true cross-core synchronization, not just a flag (§3).
2. **Atomic rename for WAV files** — write to `.tmp`, rename on success, so a crash mid-write can never produce a half-written file that the upload scanner picks up.
3. **PSRAM allocation must be checked, not assumed** — `heap_caps_malloc` silently returns `nullptr` if `board_build.arduino.memory_type` is misconfigured; this is the most build-config-fragile part of the whole project and deserves an explicit check + halt-and-blink/serial-log rather than a null-pointer crash.
4. **DST edge case around the 3am window** — once/year the "hour == 3" check can double-fire or get skipped during a DST transition; low risk given the retry-tolerant design, not worth extra engineering, just worth a one-line note in the plan so it's not mistaken for a bug later.
5. **Flash-level secret exposure** — baking WiFi/MinIO credentials as literal `#define` strings means anyone with physical flash access can `strings` them out. Fine for v1 on a private home LAN (matches your explicit build-time-injection preference), but call out flash encryption as a future hardening step, explicitly out of scope now.
6. **Unbounded SD growth on repeated upload failure** — no monitoring was requested, but note it as a known limitation; a cheap addition (not mandatory) would be logging free SD space once a day.
7. **Bring-up order recommendation:** validate PDM mic capture → SD write in isolation first (record N seconds, no networking at all) as the first milestone, before adding WiFi/MQTT/SigV4. This is the highest-risk hardware integration point (I2S-PDM support on S3 across core versions) and should be de-risked before layering the network stack on top.
